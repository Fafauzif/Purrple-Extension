# Calendar in Purrple 2.0

Use Calendar to reserve time for a task, add a standalone block, or check when work is due. Calendar works locally in Firefox, Brave, and Chrome. Week opens by default on wide screens. Narrow views begin in Agenda. Day shows the all-day and timed lists for one date. The Calendar date picker and previous, next, and Today controls are keyboard operable.

Select a block to reschedule, resize, remove, or begin focus. Drag a block to a date to open the editor with that date filled in. Enter a different start time or duration in the editor. Review the preview before saving. Undo last change restores the previous calendar operation, including a removed block. An overlap or a time outside 8 a.m. to 6 p.m. on weekdays is advisory. Archiving a task preserves its blocks and history. To free a future slot, remove the block separately. Existing task deadlines stay in place when blocks move. Finished focus and breaks appear at the time the timer ended, with the elapsed duration from the session log. These entries leave the planned block intact and do not imply an uninterrupted work period.

Dates printed on all-day items and date-only deadlines use the recorded civil date. Timed blocks store their original local date, clock time, zone, clock-overlap choice, and UTC instants. Changing the device zone changes their display time. Editing a timed block uses the block's original zone, shown in the preview. Dragging it to a date uses the current display zone. A timed block crossing midnight appears on both dates it covers. External all-day end dates are exclusive. If a clock change skips a selected time, choose a different start. If it repeats that time, choose its first or second occurrence. The entered duration is elapsed time, including across a clock transition. Repeats create up to 52 daily or weekly occurrences in one save. Each has a stable identifier, so moving or removing one leaves the others in place. A series containing a skipped start time asks you to revise the schedule before saving.

## Existing Firefox Google helper

The optional [local helper](CALENDAR.md) reads the next seven days of the primary Google Calendar and can create an event after explicit review. Its Firefox permission, setup, and authorization stay in Settings. The new Calendar surfaces its commitments from the same fetch, with Google labels, read-only details, and explicit copy to a local task. That task keeps its source reference after the event or account is removed. The helper's existing 100-item limit applies. A failed refresh shows the last successful results for the same connection while that view remains open. Losing or switching the connection clears its events from the view. Cached events and credentials stay out of portable backups. The helper's Google consent is separate from Firefox permission. It is available in Firefox only.

## Hosted Google Calendar pilot

The hosted pilot is a later release. This build provides event normalization, account-bound view state, synthetic provider fixtures, and the contract below. The extension ships without a hosted endpoint, a Google sign-in control for the pilot, or a requirement to connect an account.

| Operation | Pilot behavior |
| --- | --- |
| Status | Return disconnected, connected, limited, stale, or revoked for the authenticated caller. Include last completed refresh and recoverable failure per selected calendar. |
| Connect | Issue a short-lived Nango Connect session restricted to the pilot's Google Calendar integration and a single pending enrollment. Map the resulting connection only after a server-side check. |
| List calendars | Offer permitted calendar IDs and display names. Persist explicit selection on the server for this caller. |
| List range | Return only authorized calendars within the bounded complete range. Pass occurrence identity, start and end, read-only title and link, and completeness per calendar. |
| Disconnect | Revoke the server mapping, cancel future refresh, remove cached Google events and complete explicit provider disconnect. Keep any copied tasks. |
| Create or update | Return unavailable during the read-only pilot. Add write consent separately if a later release publishes work blocks. |

The owner configures Google OAuth, a Nango environment and a thin Cloudflare Worker once. Issue the two pilot accounts individually an expiring, single-use enrollment code, store only a digest, and exchange it for a high-entropy installation credential bound to an internal account record. Store only a credential digest on the server with status and expiration. Rotate through a caller-authenticated endpoint that invalidates the old credential when a replacement is acknowledged. Revoke lost installations from the owner console. A reported installation ID never authorizes a request. Keep installation credentials in extension-local privileged storage outside the planner save, content scripts, logs, and backups. Restrict pilot access to enrolled accounts. Mitigate request replay through short-lived enrollment and connection tokens, HTTPS, token expiration, and per-caller request limits.

Authenticate before creating the Connect session, tag it for the verified account and a pending enrollment nonce, and restrict allowed integrations to the pilot's Google configuration. Keep the Google and Nango credentials on their corresponding servers. On completion verify a signed Nango webhook or fetch server-side connection metadata, check the integration and pending nonce and account tags, and atomically claim the single resulting connection for that account. Ignore a connection ID supplied by a client unless it matches the stored server mapping. Check authorization again on every calendar-list, range and disconnect request. Reject and test cross-account substitution, expired enrollment, duplicate enrollment, revoked credential, stale Connect sessions, and delayed duplicate callbacks. [Nango Connect](https://nango.dev/blog/how-to-migrate-from-composio-to-nango)

Request `calendar.events.readonly` and `calendar.calendarlist.readonly`. Use a selected calendar allowlist, page until each bounded range is complete, expand recurrence with `singleEvents=true`, and retain `recurringEventId` and `originalStartTime` so a moved instance keeps its identity. Preserve all-day date values and omit or remove canceled instances. Send only IDs, display title, link and interval fields required by Calendar. Refresh Today and the visible date range with a modest buffer at startup, on view opening if stale, and periodically while the browser is open. Coalesce duplicate fetches, obey retry guidance and per-account limits, and replace each calendar's cache only once its range is complete. Show stale or revoked status and offer Retry or reconnect. Leave local actions accessible throughout. If incremental sync is added later, keep consistent query parameters, store the final page's sync token, and reset the affected cache on HTTP 410 before full resync. [Calendar scopes](https://developers.google.com/workspace/calendar/api/auth) · [List events](https://developers.google.com/workspace/calendar/api/v3/reference/events/list) · [Recurrence](https://developers.google.com/workspace/calendar/api/guides/recurringevents) · [Incremental sync](https://developers.google.com/workspace/calendar/api/guides/sync)

Before running the two-account pilot, confirm Google testing users and OAuth review requirements. Two Google accounts use two Nango connections even when each selects multiple calendars. Nango lists 10 included connections, 10 compute hours and 10 GB monthly transfer on Free. Check actual quotas and hosting requirements before launch. Keep the local helper available until a later release changes the integration.
